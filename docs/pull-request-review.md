# Revisão, merge e ajustes (Git local)

`GET /.../executions/{id}/review` devolve a projeção persistida. `POST /review/refresh` consulta o Git local; `POST /review/approve` registra a aprovação independente do commit publicado. As escritas exigem sessão/CSRF e acesso ao projeto. Outra pessoa da organização deve aprovar: quem iniciou a execução não aprova o próprio resultado.

A consulta depende de `Local:EnableReview=true` (padrão `false`) e de uma execução `Succeeded` com `tests_passed`. `LocalGit` lê a ref `teamflow/<executionId>` e confere que o head é o publicado, que o primeiro parent é a base do snapshot e se a branch base já aponta esse head. Os campos `ciPassed` e `merged` do contrato significam, respectivamente, "head e base verificados com os testes do runner" e "fast-forward confirmado". Não há CI externo nem checks de terceiros.

A aprovação fixa o head, exige essa verificação e mantém a tarefa em `AwaitingMerge`. A tarefa só vira `Done` com merge confirmado: head esperado, revisor ainda membro, primeiro parent igual à base validada e base == head. O aplicativo não executa o merge: a pessoa responsável faz `git merge --ff-only teamflow/<executionId>` na branch base e consulta de novo. Squash, rebase e outros merges exigem revalidação.

Se código ou base mudarem, a aprovação é invalidada e a tarefa volta a Review com `revalidation_required`. Merge sem aprovação confirmada fica `merge_policy_unverified` e não conclui a tarefa. Uma consulta atrasada não sobrescreve outra mais nova: versão da tarefa e lock compartilhado com o agendamento protegem a atualização, e uma nova execução impede que a revisão antiga conclua a tarefa. Merge já confirmado permanece confirmado.

Solicitar ajustes reutiliza `POST` de execuções com `ParentExecutionId`, `Feedback` (até 2000 caracteres), `Version` e `Idempotency-Key`. A transação preserva descrição, critérios e histórico, adiciona o feedback ao objetivo e cria uma execução ligada à anterior; repetir devolve a mesma. O perfil anterior é herdado se não houver outro e precisa continuar ativo. A execução nova usa branch própria, a anterior permanece como referência, e a transferência de alterações e contexto segue [agent-transfer.md](agent-transfer.md).
